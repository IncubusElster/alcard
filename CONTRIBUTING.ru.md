# Участие в разработке Alcard

[English](CONTRIBUTING.md) · **Русский**

Начните с [обзора](docs/ru/overview.md), [активного плана](docs/ru/roadmap.md) и [руководства по сборке](docs/ru/building.md). Alcard предназначен для Alpine aarch64 и Cardputer Zero. Опирайтесь на текущий код, документированные контракты и область приёмки.

## Границы компонентов

| Область | Ответственность |
| --- | --- |
| Workspace `rust/` | Ratatui Settings/Hello, setup backend и общие crates без GUI |
| `rust/crates/alcard-ui` | Общая графическая отрисовка; самостоятельный workspace |
| `rust/apps/alcard-shell` | Управляемая клавиатурой Shell и ограниченный radio helper; самостоятельный workspace |
| `rust/apps/alcard-polkit-agent` | Графическая polkit-авторизация; самостоятельный workspace |
| `rust/apps/alcard-lock` | Native session lock и PAM conversation; самостоятельный workspace |
| `packaging/apk`, `scripts`, `tools` | Входные данные пакетов, сборка и проверки |
| `board`, `patches`, `keyboard-zero`, `fonts` | Аппаратные исходники, раскладки/шрифты и адаптации upstream |

Сохраняйте все пять Cargo lockfiles. Console не должен получать Wayland или GLib через общий crate. Новые системные операции настроек относятся к общей функциональности; авторизация и отрисовка конкретного UI остаются ответственностью frontend. Существующий контракт первого запуска `--hello` и три режима установки выбраны намеренно.

## Проверки по характеру изменения

Изменения документации и лицензии начинаются с:

```sh
bash build.sh audit
python3 tools/check-docs.py
```

Для Rust используйте нужный workspace с lockfile, поддерживаемым toolchain и native-библиотеками. Типовая проверка консольных исходников:

```sh
cargo fmt --manifest-path rust/Cargo.toml --all --check
cargo test --manifest-path rust/Cargo.toml --locked --workspace --all-targets
cargo clippy --manifest-path rust/Cargo.toml --locked --workspace --all-targets -- -D warnings
```

Графические исходники, native-авторизация, установленные APK и настоящий VT/VM имеют дополнительные требования; см. [проверки](docs/ru/testing.md). Native fixture-скрипты могут создавать пользователей, менять конфигурацию изолированных служб и загружать гостевые системы. Запускайте их только в документированном контейнере/VM.

Держите тесты в отдельных файлах `unit_tests`/integration, подключаемых только при тестировании. Production-пакеты используют release-бинарники и не должны содержать test harness, примеры и fixtures. Проверяйте поведение на изменяемой границе: поиск строки в исходнике не заменяет сценарий PAM, NetworkManager, BlueZ или композитора.

Используйте единый CI workflow с одним runner и последовательными этапами. Изменения только документации проходят статическую проверку; изменения кода/сборки добавляют проверки исходников в Alpine. Полная приёмка установленных пакетов, VM и Hello выбирается вручную. Перед удалённым прогоном прочитайте [руководство по проверкам](docs/ru/testing.md); запускайте уровень, необходимый для изменённой границы.

## Пакеты и выпуск

APKBUILD — источник метаданных пакета. Сборщики и верификаторы читают версии, имена файлов и идентификаторы ядра через [package_metadata.py](tools/package_metadata.py), который разбирает объявления без выполнения рецепта. Меняйте объявления рецептов и точные зависимости вместе; не добавляйте ещё один список версий в скрипт. Новая декларация в исходниках не означает новую принятую бинарную сборку.

Для приёмки записывайте commit исходников, toolchain, версии пакетов и хеши результатов. Различайте проверки исходников, установленных пакетов, VM и физического устройства. Приватные ключи подписи и dev credentials должны оставаться вне отслеживаемых файлов; локальное состояние сборки размещается в `.alcard-local/`.

## Документация и перевод

Основной язык — английский. У каждой темы в `docs/en` есть одноимённый файл в `docs/ru`. Меняйте обе редакции вместе: ссылки переключения языка, дату обновления, команды, идентификаторы и ограничения. Русский текст — полный технический перевод, а не сокращённое резюме. Корневые README и руководства участия/безопасности также имеют русские версии.

Не переводите машинные идентификаторы: флаги CLI, имена пакетов, пути, ключи конфигурации, хеши и буквальные варианты Hello `Graphics`, `Graphics Minimal`, `Console`. Пояснения переводите естественно. В обеих редакциях различайте состояние реализации и состояние приёмки.

Действующие контракты находятся в тематических руководствах, границы готовности — в [текущем статусе](docs/ru/status.md). Логи CI и машиночитаемые результаты относятся к артефактам прогонов. Храните сведения о происхождении релиза вместе с распространяемым релизом. Поддерживайте один активный план; не добавляйте дневники разработки, карты переноса и устаревшие спецификации в текущее дерево исходников.

Сохраняйте уведомления upstream и записывайте заимствованные материалы в [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md); аппаратные и шрифтовые исключения сохраняют собственные условия. Для сообщений о проблемах безопасности используйте [SECURITY.ru.md](SECURITY.ru.md). Обычный отчёт об ошибке должен содержать версию исходников/пакетов, режим установки, устройство или VM, шаги воспроизведения, ожидаемое поведение и очищенный журнал. Перед публикацией убирайте пароли, приватные ключи, токены и ненужные личные/сетевые идентификаторы.
