# Boot, updates, and recovery

**Language:** English · [Русский](../ru/boot-updates.md)

> Scope: current source tree · Updated: 2026-11-22

Alcard uses persistent Alpine sys-mode: one ext4 ROOT holds the operating system, the APK database, configuration, and user data. The image builder creates three FAT partitions beside ROOT. Currently, all three FAT partitions contain the same boot files and the image boots through the first partition. **A/B boot transactions, automatic trial boot, health confirmation, and rollback are design work; the updater is not implemented.**

This distinction matters when interpreting a successful build. Offline verification can inspect an image and its files; it does not prove that CM0 firmware boots it, that a trial slot falls back, or that a power interruption is recoverable. See [current status](status.md) for current readiness and [testing](testing.md) for the current evidence boundaries.

## Current image layout

The implementation is [build-image-zero.sh](../../scripts/build-image-zero.sh) with the regular-file image writer [image-zero.py](../../tools/image-zero.py). It writes an MBR partition table and four partitions:

| Partition | Filesystem label | Filesystem | Default size | Current contents and intended role |
| --- | --- | --- | --- | --- |
| 1 — BOOT-SELECT | `ALCARDSEL` | FAT32 | 64 MiB | A complete bootable copy of the current payload; intended future home of the early firmware and selector |
| 2 — BOOT-A | `ALCARDA` | FAT32 | 128 MiB | The same payload; intended future independent slot A |
| 3 — BOOT-B | `ALCARDB` | FAT32 | 128 MiB | The same payload; intended future independent slot B |
| 4 — ROOT | `ALCARDROOT` | ext4 | 2048 MiB | Persistent `/`, including `/usr`, `/etc`, `/var`, the APK database, and `/home` |

The build-time controls are `ALCARD_SELECT_MIB`, `ALCARD_BOOT_MIB`, and `ALCARD_ROOT_MIB`. `ALCARD_BOOT_MIB` applies to both boot slots. The full-image wrapper requires ROOT to be at least 1024 MiB and checks that staged rootfs usage fits within 75% of the selected capacity. These are development defaults and a capacity check, not a measured release sizing or old/new kernel retention budget. The image does not automatically assign the remainder of a physical card to ROOT.

There is no alternate ROOT, separate home partition, Btrfs deployment, OSTree deployment, or rootfs snapshot mechanism. Future per-user `fscrypt` support is a separate storage feature. It would not turn the boot layout into full-system rollback or replace backups.

The writer works with regular files, creates the filesystems without host loop mounts, verifies a temporary image, and replaces the output file. It refuses block-device output and unsafe symlink destinations. Producing the file is separate from writing a microSD card; follow [installation](installation.md) for that boundary.

## Boot files and configuration ownership

The image uses the Alpine kernel and Raspberry Pi boot firmware. Alcard supplies its board DT overlays, device firmware, and external modules. The current kernel package is pinned to `linux-rpi=6.18.60-r0`, with module ABI `6.18.60-0-rpi`; see [packaging](packaging.md) for the complete source package inventory.

| Component | Owner and current location |
| --- | --- |
| Kernel, base DTB, Raspberry Pi boot firmware | Alpine packages staged under rootfs `/boot` |
| Initramfs | Generated by Alpine `mkinitfs` for the selected ABI after the rootfs is installed |
| Alcard DTBO files | `alcard-boot-zero`, installed under `/boot/overlays` |
| `/boot/alcard.cfg` | Exactly one board profile: `alcard-board-zero-v5` or `alcard-board-zero-v5-lite` |
| Final FAT `config.txt` and `cmdline.txt` | Generated by the image builder when it copies the staged boot payload into each FAT |
| Module trees and device firmware | Installed in the common ext4 ROOT by the kernel/BSP packages |

Before copying the payload, the builder requires nonempty `vmlinuz-rpi`, `initramfs-rpi`, `bcm2710-rpi-cm0.dtb`, `bootcode.bin`, `start.elf`, `fixup.dat`, `alcard.cfg`, and `overlays/alcard-zero-v5.dtbo`. This is a file contract, not proof that the particular CM0 firmware path accepts every file and configuration.

The generated `config.txt` is identical in all three FAT partitions:

```ini
[all]
arm_64bit=1
kernel=vmlinuz-rpi
initramfs initramfs-rpi followkernel
include alcard.cfg
```

Each `cmdline.txt` is one line in this form; `DISK_ID` represents the image's generated eight-digit MBR disk identifier:

```text
console=tty1 root=PARTUUID=DISK_ID-04 rootfstype=ext4 rootwait rw
```

The root filesystem's `/etc/fstab` contains:

```fstab
LABEL=ALCARDROOT / ext4 rw,noatime 0 1
```

No FAT mount is configured by this fstab. `/boot` in ROOT is currently a package staging directory; it is not automatically the active FAT partition. A later `apk` transaction that writes to that directory does not by itself update the files read by the firmware. Conversely, mounting an active FAT there would allow package writes to modify the working boot path directly. The future updater must resolve this ownership and mount contract explicitly.

The common boot APK does not edit the user's `config.txt`, insert a root identifier, or activate A/B. The image builder owns the single `include alcard.cfg`. Keep the profile mutually exclusive, preserve the exact root identifier, and avoid importing `/boot/firmware` conventions from a different distribution. Board pin conflicts, LCD startup dependencies, and standard/Lite differences are documented in [hardware](hardware.md).

## Image creation, identity, and verification

Use the full [build guide](building.md) to prepare the build environment, signing keys, hardware APKs, and all nine user/session APKs. With those prerequisites present, the profile-specific image commands are:

```sh
bash build.sh image-check-v5
bash build.sh image-v5
bash build.sh image-verify-v5

bash build.sh image-check-lite
bash build.sh image-v5-lite
bash build.sh image-verify-lite
```

The standard image is `.alcard-local/images/alcard-zero-v5-0.1.0.img`; the Lite image is `.alcard-local/images/alcard-zero-v5-lite-0.1.0.img`. Each has a `.img.sha256` sidecar and a JSON manifest with the same basename and `.json` extension.

The `Alcard-image-v1` JSON records the profile, MBR disk ID, root PARTUUID, root UUID, partition layout, and the note that automatic tryboot is disabled. It is not yet a complete release provenance manifest: it does not enumerate all package versions, source commits, build inputs, or the developer-root mode. Disk IDs and root UUIDs are generated for each build, so the current workflow does not promise byte-identical images from two invocations.

[verify-image-zero.sh](../../scripts/verify-image-zero.sh) checks the checksum and runs structural and deep verification. [verify-image-deep-zero.py](../../tools/verify-image-deep-zero.py) examines the final image, including FAT contents, profile selection, ext4 consistency, installed packages and services, permissions, module ABI/indexes, firmware, and the initramfs archive. This is stronger evidence than inspecting only the staging directory. It remains offline evidence and must be associated with the exact image that passed it.

The current complete Cardputer image needs its own acceptance. BSP image checks and QEMU userland checks on `linux-virt` do not establish physical Raspberry Pi boot, LCD operation, power management, or A/B recovery.

## Normal first boot and explicit developer root

The default is `ALCARD_DEV_ROOT=0`. A normal image keeps root locked for initial setup and uses the single `tty1` dispatcher to choose Hello or the configured login/session path. A stale local password-hash file is ignored unless the build explicitly enables developer root. See [installation](installation.md) and [security](security.md) for the setup and account contracts.

Setting `ALCARD_DEV_ROOT=1` enables the existing local development path. It requires `.alcard-local/dev-root-password.hash` to be a nonsymlink regular file with mode `0600` and a single SHA-512 crypt hash beginning with `$6$`. The builder installs that hash into root's shadow entry. This unlocks root and prevents automatic Hello on first boot; it is not the normal onboarding image. No default plaintext developer password is defined by this path.

Two implementation gaps must be addressed before release artifacts can be distinguished reliably:

- Developer and normal builds use the same image filename, checksum filename, and manifest filename. A build can replace the other mode's artifacts, and the manifest has no developer-root flag.
- The deep verifier does not enforce a release policy of a present, locked root entry. Its current warning branch classifies a missing or empty root password field together with locked values, and an unlocked developer hash does not make verification fail. A successful image verification is therefore insufficient evidence that developer credentials are absent.

These observations concern artifact identity and verification. They do not mean that the builder enables developer root by default. Keep development artifacts clearly separated in release handling until distinct naming, explicit manifest state, and a strict credential gate are implemented.

## Update invariants

A successful package transaction is only one part of a safe boot update. The candidate that firmware will actually load must satisfy all of these conditions:

| Object | Required invariant |
| --- | --- |
| Kernel and modules | Loaded kernel release exactly matches a complete `/usr/lib/modules/<ABI>` tree and module indexes |
| Initramfs | Regenerated for that ABI, with the modules and firmware needed before ROOT is available |
| DTB and overlays | Match the board profile and BSP; no conflicting devices, addresses, or pin assignments |
| LCD firmware | The name requested by the panel's `compatible` exists where the firmware loader needs it |
| Root selection | `cmdline.txt` names the intended persistent ext4 ROOT by the correct stable identifier |
| Destination | The updater has identified and mounted the actual inactive FAT, not an empty directory on ROOT |
| Candidate identity | A manifest and hashes describe the complete staged boot set and its corresponding ROOT dependencies |
| Previous boot set | Remains untouched until the candidate has booted and passed health checks |
| Shared ROOT | Keeps the previous ABI's modules and compatible firmware throughout the trial |
| User data | Remains on ROOT; backups and rootfs migration policy are handled separately from boot-slot switching |

The BSP's exact kernel dependency and the image's APK world pin help avoid an accidental ABI change. They do not make FAT updates atomic or preserve old modules automatically. There is no public Alcard APK repository yet; locally built signed APKs and the installed Alpine repositories are the current inputs. A public repository, trusted key distribution, immutable package retention, and a release update policy remain work to do.

For a future kernel change, update the kernel, development headers, external modules, DT/initramfs assumptions, and verifier expectations together. Validate dependency resolution with `apk upgrade --simulate` against newer upstream indexes before attempting an actual update. Keep the exact upstream APK artifacts in an immutable binary cache or snapshot outside Git; mirrors may stop carrying the pinned revision. Do not solve a dependency refusal by forcing a mismatched kernel or headers.

Continue using the official Alpine kernel unless a verified requirement demands a change. If the kernel configuration becomes insufficient, start from the pinned Alpine recipe and a narrow configuration/patch set; a copied Linux source tree is not needed merely to package external modules. Reboot requirements for kernel, DT, and boot firmware changes remain even when one individual module can be reloaded at runtime.

## Intended A/B mechanism

The design uses Raspberry Pi firmware selection through `autoboot.txt`, `boot_partition`, and one-shot tryboot. It concerns CM0's boot ROM/firmware path, not a Pi 5 EEPROM update mechanism. The exact `bootcode.bin`, `start.elf`, and `fixup.dat` supplied by Alpine must first be tested on CM0, including first-partition file lookup and booting FAT partitions 2 and 3. The first partition may need a valid fallback payload as well as the selector.

The following are **design examples, not files generated by the current installer**. With A active, the proposed selector is:

```ini
[all]
tryboot_a_b=1
boot_partition=2
[tryboot]
boot_partition=3
```

After a one-shot boot of B has passed validation, the committed selector would be:

```ini
[all]
tryboot_a_b=1
boot_partition=3
[tryboot]
boot_partition=2
```

The proposed trial request is `reboot '0 tryboot'`. It is a design detail, not a bring-up command to run before the exact CM0 firmware and partition mapping have been validated. The current builder installs neither these selector examples nor automatic tryboot behavior.

The updater must implement the following state transitions:

| Phase | Required action and completion condition |
| --- | --- |
| ACTIVE(A) | Record the working slot, hashes, kernel ABI, and compatible ROOT dependencies |
| PREPARE(B) | Copy a complete candidate to the actual inactive FAT; leave A and the selector untouched |
| VERIFY(B) | Sync and verify hashes, ABI, initramfs, merged DT, firmware names, configuration, and root PARTUUID |
| TRIAL(B) | Request exactly one boot of B through the verified firmware mechanism |
| VALIDATE(B) | Confirm slot identity, ext4 root, kernel/module agreement, critical OpenRC services, input, DRM, and acceptable power state |
| COMMIT(B) | Persist the selector only after health confirmation, using a recoverable write procedure; retain A |
| FAILED(B) | Do not commit; reset/reboot to the previous selector and verify that the trial flag has cleared |

A kernel reaching userspace is not sufficient confirmation. A hung candidate also does not reboot itself: watchdog behavior or a manual power cycle must be validated on hardware. The selector is still on FAT, so changing a small file is not automatically a power-loss-safe commit. The updater needs synchronization, backup/recovery, and interruption tests for that write.

An older boot slot uses the same changed ROOT. Returning to A does not restore the APK database, userland packages, configuration, or databases. Retaining both module ABI trees and compatible firmware is essential; otherwise the old kernel can return without usable modules. Early boot updates must stay within a defined ROOT compatibility window. Incompatible userland migrations need their own recovery and backup policy.

## Recovery and acceptance gates

Keep the factory microSD and a separate known-working Alcard card during bring-up. A tested recovery copy must preserve a coherent kernel, DT, initramfs, firmware, and module set, not just a previous kernel file.

If the built-in display fails, HDMI, UART, or SSH can be useful only when the hardware route and access have already been configured and verified. Do not assume network access or an open SSH service exists. Use a card reader with the device powered off to inspect or restore damaged boot files; preserve the ext4 ROOT when it is healthy, and back up user data before operations that can overwrite it. Encryption does not provide a backup.

If an update leaves boot assets and ROOT dependencies inconsistent, do not report it as successful or deliberately reboot into that state. Restore a coherent set first. Automatic reversion to another FAT is unavailable in the current implementation, so recovery instructions must not depend on it.

Before enabling automated A/B updates, complete these gates:

1. Boot the current full image on the actual standard and Lite hardware profiles and record exact firmware/kernel/package identities.
2. Verify CM0's early first-partition file requirements and selection of partitions 2 and 3 with the shipped firmware.
3. Prove the one-shot trial flag, normal reboot fallback, and behavior after a hang or power cycle.
4. Implement boot staging and mount protection so APK hooks never modify the active FAT directly.
5. Preserve the previous kernel ABI and compatible firmware on the common ROOT throughout a trial.
6. Implement independent slot manifests, health confirmation, safe-power checks, and recoverable selector writes.
7. Test interrupted writes, failed health checks, damaged selectors, and documented SD-card recovery on real devices.
8. Strengthen release artifact identity and the locked-root verifier, then accept the exact candidate image under those rules.

No runtime updater, hardware acceptance, or release verification is added by this documentation update. The remaining engineering work is tracked in the [roadmap](roadmap.md).
