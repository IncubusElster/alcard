# Сборка Alcard

**Язык:** Русский · [English](../en/building.md)

> Область: текущее дерево исходников · Обновлено: 2026-11-22

Это полный путь от рабочей копии репозитория до подписанных пакетов и офлайн-образа Cardputer. Он использует существующие скрипты и постоянный Distrobox с **Alpine 3.24 aarch64**. Успешная сборка не является физической приёмкой Cardputer; см. [проверки](testing.md).

## Сборочное окружение

На хосте нужны Git, Bash, Python 3, rootless Podman и Distrobox. Статический аудит запускает Python непосредственно на хосте; используйте Python 3.11+, чтобы также поддерживать остальные Python-инструменты репозитория. На x86-64 должны заранее работать QEMU user-mode/binfmt для ARM64. Сборочные скрипты не устанавливают пакеты хоста, не создают Distrobox и не записывают физическую SD-карту.

Клонируйте репозиторий с обычным доступом к GitHub и работайте из его корня:

```sh
git clone https://github.com/IncubusElster/alcard.git
cd alcard
bash build.sh help
```

`build.sh` исполняемый; явный запуск через `bash` также поддерживается. Пути определяются относительно рабочей копии, а не домашнего каталога сопровождающего. Входные данные сборки, кеши, локальные настройки подписи и артефакты должны находиться в игнорируемых локальных каталогах, а не в коммитах исходников.

На хосте проверьте выполнение ARM:

```sh
podman run --rm --platform linux/arm64 docker.io/library/alpine:3.24 uname -m
```

Ожидается `aarch64`. Ошибка `exec format error` означает, что эмуляция хоста не готова. Сначала настройте binfmt/QEMU поддерживаемым способом своего дистрибутива.

Создайте контейнер один раз, если его ещё нет:

```sh
distrobox create --name alcard-arm64 \
  --image docker.io/library/alpine:3.24 \
  --additional-flags "--platform=linux/arm64"
distrobox enter alcard-arm64
apk --print-arch
exit
```

Сохраняйте рабочий `alcard-arm64`: обычные сборки используют его повторно. `ALCARD_BUILD_BOX` переопределяет имя. Рабочая копия должна быть доступна Distrobox по тому же абсолютному пути, который используют команды хоста: сборочные скрипты вызываются по этому пути.

## Однократная установка зависимостей

Выполните следующие команды **на хосте**. Root используется только внутри существующего rootless-контейнера:

```sh
ALCARD_KERNEL_VERSION="$(python3 tools/package_metadata.py kernel-version)"
podman exec --user 0 alcard-arm64 apk update
podman exec --user 0 alcard-arm64 apk add \
  alpine-sdk bash git python3 dtc kmod \
  coreutils findutils grep sed tar gzip mawk \
  bc perl bison flex openssl-dev elfutils-dev \
  "linux-rpi=$ALCARD_KERNEL_VERSION" "linux-rpi-dev=$ALCARD_KERNEL_VERSION" \
  cargo rust rustfmt rust-clippy pkgconf \
  libxkbcommon-dev wayland-dev glib-dev polkit-elogind-dev linux-pam-dev \
  py3-fonttools py3-pillow kbd \
  dosfstools e2fsprogs e2fsprogs-extra mtools mkinitfs cpio
```

Используйте согласованные репозитории `v3.24/main` и `v3.24/community`. Не добавляйте `edge` в это сборочное окружение. Если закреплённые пакеты ядра исчезли с зеркала, восстановите соответствующий доверенный снимок пакетов либо подготовьте согласованное обновление BSP; замена только версии заголовков не исправляет проблему.

| Группа | Для чего нужна |
| --- | --- |
| `alpine-sdk`, архиваторы, Git | `abuild`, компиляторы, подготовка исходников/архивов и подпись |
| Точные kernel/dev-пакеты, Kbuild-инструменты, `dtc`, `kmod` | Внешние модули, ABI/символы и DTBO |
| Штатный Rust Alpine и библиотеки для разработки | Консольные и независимые графические программы |
| Python 3.11+, fontTools, kbd | TOML firmware, генерация шрифтов и бинарные консольные карты |
| Инструменты файловых систем, `mkinitfs`, `cpio` | Создание и проверка FAT/ext4-образа без устройства |

Предварительная проверка native-исходников требует Rust **1.96.1 или новее**; минимум в manifests — **1.96**. Сборщики намеренно используют `/usr/bin/cargo`, `/usr/bin/rustc` и `/usr/bin/rustdoc` с отдельными кешами aarch64/musl. Обёртка rustup хоста в общем домашнем каталоге Distrobox их не заменяет. Образу устройства не нужны компилятор, заголовки ядра, fontTools и инструменты проверки образа только потому, что ими пользуется сборщик.

Зависимости исполнения разрешаются при создании одноразовой целевой rootfs. Установка labwc или NetworkManager на сборочный хост не подтверждает правильность зависимостей целевых пакетов.

## Однократная настройка подписи APK

Создайте ключ от обычного пользователя сборки внутри Distrobox:

```sh
distrobox enter alcard-arm64
abuild-keygen -a -n
printf '%s\n' "$HOME"
ls -l ~/.abuild/*.rsa.pub
exit
```

`-a` записывает расположение приватного ключа в конфигурацию abuild пользователя. `-n` делает генерацию неинтерактивной. Опция `-i` здесь не нужна: она пытается привилегированно установить публичный ключ и может не работать в rootless Distrobox.

Используйте напечатанный путь домашнего каталога сборочного пользователя: он может быть под `/home` или `/var/home`. Откройте root shell внутри того же контейнера:

```sh
podman exec -it --user 0 alcard-arm64 /bin/sh
```

В этой контейнерной shell задайте фактический путь и установите **только публичные ключи**:

```sh
ALCARD_SIGNING_HOME=/actual/build-user/home
install -d -m 755 /etc/apk/keys
install -m 644 "$ALCARD_SIGNING_HOME"/.abuild/*.rsa.pub /etc/apk/keys/
exit
```

Замените `/actual/build-user/home` перед выполнением. Приватные `.rsa` должны оставаться вне Git и обычных артефактов. Ключ локальной проверки не становится автоматически ключом будущего публичного релиза. Сборщики пакетов запускаются обычным пользователем и отклоняют выполнение Cargo/abuild от root. `abuild -d` ожидает подготовленные зависимости и не устанавливает их во время сборки.

## Статическая проверка

Из корня репозитория на хосте:

```sh
bash build.sh audit
```

Проверяются синтаксис исходников, файлы, пакетные ограничения и каталоги локализации. Эта команда не собирает Rust и не доказывает, что зеркало Alpine разрешит каждый пакет. Следующий `doctor` предназначен для модулей ядра и не является общей проверкой всех пользовательских/сессионных и образных зависимостей.

## Сборка аппаратных пакетов

Для полного образа Cardputer соберите общий BSP и оба пакета профиля. В каждый конечный образ устанавливается только один профиль.

```sh
bash build.sh doctor
bash build.sh kmods
bash build.sh firmware-check
bash build.sh firmware
bash build.sh boot-check
bash build.sh boot
bash build.sh bsp-check
bash build.sh bsp
bash build.sh board-v5-check
bash build.sh board-v5
bash build.sh board-lite-check
bash build.sh board-v5-lite
bash build.sh verify-bsp
bash build.sh verify-bsp-lite
bash build.sh install-check
bash build.sh install-verify
bash build.sh install-verify-lite
```

Сборщик модулей выбирает поставщиков по точным `.config` и `Module.symvers` ядра. Конфликт BQ27xxx/поставщиков — намеренная остановка; нельзя принудительно добавлять дублирующий модуль в пакет. Правила выбора описаны в [аппаратной части](hardware.md).

`verify-bsp*` проверяет подписи, ABI модулей, хеши firmware, объединённый DT и нужные Kconfig. `install-verify*` использует `.alcard-local/verify/install-rootfs/` с `apk --root --usermode --no-scripts`, затем проверяет индексы модулей. Это проверяет разрешение пакетов без изменения `/boot` хоста, но не выполняет все пакетные скрипты и не создаёт загрузочный образ.

Для проверки только пользовательской среды в QEMU достаточно следующего раздела: BSP Cardputer не является ядром виртуальной машины.

## Сборка всех девяти пользовательских/сессионных пакетов

Из корня репозитория на хосте, от обычного пользователя:

```sh
bash build.sh keyboard-check
bash build.sh keyboard
bash build.sh fonts-check
bash build.sh fonts
bash build.sh fonts-gui-check
bash build.sh fonts-gui
bash build.sh desktop-check
bash build.sh desktop
bash build.sh hello-check
bash build.sh hello
bash build.sh shell-apk-check
bash build.sh shell-apks
bash build.sh shell-install-verify
```

Первые пять команд собственно сборки создают клавиатуру, консольные шрифты, графические шрифты, минимальную графическую среду и Hello. `shell-apks` добавляет Shell, агент polkit, блокировщик и основной графический сеанс. Все девять пакетов нужны нынешним сборщикам полного образа; Console выбирается при первом запуске, а не отдельным флагом сборки образа.

Результат находится в `.alcard-local/packages/alcard/aarch64/`, включая архитектурно-независимые пакеты в aarch64-репозитории. Команды метаданных из [упаковки](packaging.md) показывают ожидаемые ревизии и имена файлов непосредственно из APKBUILD. `shell-install-verify` проверяет подписи и выполняет реальную изолированную установку в `.alcard-local/session-install/rootfs/`, проверяя владельцев файлов, права, AArch64/musl ELF, библиотеки и помощников авторизации. Используется root контейнера, а не хоста.

Релизные сборки используют сохранённые файлы фиксации зависимостей Cargo и `--release --locked --bins`. Проверка производственной сборки отклоняет артефакты тестов, примеров и замеров производительности и сравнивает установленные программы с релизными результатами. Компиляция нативных тестов — отдельное действие; см. [проверки](testing.md), не меняя флаги производственной сборки.

## Сборка и проверка образов Cardputer

После появления аппаратных и всех девяти пользовательских/сессионных пакетов:

```sh
bash build.sh image-check-v5
bash build.sh image-v5
bash build.sh image-verify-v5
bash build.sh image-check-lite
bash build.sh image-v5-lite
bash build.sh image-verify-lite
```

Результаты:

| Профиль | Образ | Сопутствующие файлы |
| --- | --- | --- |
| Обычная v5 | `.alcard-local/images/alcard-zero-v5-0.1.0.img` | Соответствующие манифест `.json` и `.img.sha256` |
| v5 Lite | `.alcard-local/images/alcard-zero-v5-lite-0.1.0.img` | Соответствующие манифест `.json` и `.img.sha256` |

Сборочный скрипт пересоздаёт `.alcard-local/image-stage/`, устанавливает Alpine с пакетными скриптами/триггерами, выполняет `mkinitfs` и создаёт три FAT-раздела и один постоянный ext4 ROOT. Используются обычные файлы, а не loop-устройства или физические диски. Следующая сборка того же профиля заменяет его результат. Размеры разделов по умолчанию и известные ограничения релиза описаны в [загрузке и обновлениях](boot-updates.md).

Офлайн-проверка сверяет SHA-256, MBR/разделы, содержимое FAT, ext4 через `e2fsck -fn`, UUID/PARTUUID, базу пакетов/world, профили, индексы модулей, firmware, конфигурацию служб и gzip/cpio initramfs. Она не доказывает физическую загрузку, ориентацию LCD, ввод клавиатуры или откат A/B.

## Вариант QEMU

Пользовательские/сессионные пакеты также позволяют создать одноразовый Alpine aarch64 `virt`-образ:

```sh
bash build.sh qemu-hello-check
bash build.sh qemu-hello
```

Сборщик пишет в `.alcard-local/qemu-aarch64/`, использует `linux-virt` и создаёт соответствующий скрипт запуска. Этот путь Hello через последовательную консоль отличается от приёмки входа в виртуальной машине с настоящим VT. Доступные средства запуска и их условия описаны в [проверках](testing.md). QEMU-образ не заменяет SD-образ Cardputer.

## Диагностика и сведения о релизе

| Симптом | Что проверить |
| --- | --- |
| `exec format error` до запуска контейнера | ARM64 binfmt/QEMU хоста и выбранную платформу |
| Путь Cargo существует, но файл не запускается | Штатные инструменты Alpine в `/usr/bin`; общие обёртки rustup хоста |
| Нет подписанного APK или индекса | Завершение предыдущей группы сборки, доверенный публичный ключ и фактическую ревизию рецепта |
| Конфликт реализации/неопределённый символ в kmods | Точную пару ядра/заголовков, `.config`, `Module.symvers`, выбранное семейство драйверов производителя и патч |
| Для проверки образа нет `debugfs` или `cpio` | Установить `e2fsprogs-extra` и `cpio` в сборочный контейнер |
| Rootfs образа превышает допустимую ёмкость | Осознанно увеличить `ALCARD_ROOT_MIB`; сборщик ограничивает подготовленное дерево 75% запрошенного раздела |

Не обходите проверку подписи, ABI или пакетного конфликта ради получения образа. Для приёмки сохраняйте вместе коммит исходников, файлы фиксации зависимостей Cargo, версии инструментов, разрешённый состав APK, манифест образа и хеши результатов. Тег `alpine:3.24` и репозитории ветки могут меняться, а идентификатор диска и UUID создаются заново; сборщик не обещает побайтово одинаковые полные образы.

Обычный образ оставляет root заблокированным для Hello. Явный режим developer-root описан в [загрузке и обновлениях](boot-updates.md); сейчас он использует то же имя результата и не подходит для неотличимых публичных релизных артефактов. Команда записи SD в эту последовательность сборки не входит.
