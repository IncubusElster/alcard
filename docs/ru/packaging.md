# APK-пакеты и владение файлами

**Язык:** Русский · [English](../en/packaging.md)

> Область: текущее дерево исходников · Обновлено: 2026-11-22

Alcard использует Alpine APK и для сборки образов, и для установленного ПО. В репозитории 15 рецептов: шесть аппаратных, BSP и профильных пакетов, а также девять пользовательских/сессионных. Образ выбирает один из двух профилей платы. Это количество не включает обычные зависимости Alpine, которые разрешает APK.

## Текущие версии исходных рецептов

[Файлы APKBUILD](../../packaging/apk/) определяют `pkgver`, `pkgrel`, зависимости и владение файлами. [package_metadata.py](../../tools/package_metadata.py) читает объявления без выполнения рецептов; сборщики и верификаторы используют этот общий инструмент. Перечень ниже описывает ответственность исходных пакетов. Версия рецепта сама по себе не подтверждает принятый бинарный релиз.

Читайте текущие значения непосредственно из рецептов:

```sh
python3 tools/package_metadata.py manifest
python3 tools/package_metadata.py filename --group user
python3 tools/package_metadata.py kernel-version
python3 tools/package_metadata.py kernel-abi
```

| Пакет | Ответственность |
| --- | --- |
| `alcard-kmods-rpi` | Внешние модули M5Stack для точного ABI ядра Raspberry Pi |
| `alcard-firmware-zero` | Инициализация ST7789 MIPI DBI и данные firmware BMI270 |
| `alcard-boot-zero` | Четыре общих DTBO v5 |
| `alcard-bsp-zero` | Аппаратный комплект только из зависимостей |
| `alcard-board-zero-v5` | Активная загрузочная конфигурация обычной v5 |
| `alcard-board-zero-v5-lite` | Альтернативная загрузочная конфигурация v5 Lite |
| `alcard-keyboard-zero` | Данные XKB и консольных раскладок US/RU/ES/DE |
| `alcard-fonts-console` | Консольные PSF2 Regular/Bold |
| `alcard-fonts-gui` | TTF Regular/Bold для приложений, например Foot |
| `alcard-desktop-minimal` | Резервная сессия labwc/Pixman и Foot |
| `alcard-hello` | Settings/Hello на Ratatui, служба настройки, точки входа первичной настройки и авторизации, общая конфигурация радиослужб |
| `alcard-shell` | Shell и вспомогательная программа управления радиоустройствами с ограниченными полномочиями |

Готовых `alcard-repository`, `alcard-base`, `alcard-board-zero`, профиля v3 и отдельного APK графических Settings сейчас нет. Эти имена не должны фигурировать как обязательные входы сборки. Исполняемый файл `alcard-settings` поставляется пакетом `alcard-hello`.

## Граница аппаратных пакетов

Зафиксированная база — `linux-rpi=6.18.60-r0`, ABI `6.18.60-0-rpi`. Ревизия пакета модулей `r3` не связана с ревизией пакета ядра `r0`. Соответствующий `linux-rpi-dev` нужен для сборки и не устанавливается на устройство только ради работы модулей.

| Владелец | Устанавливаемые файлы |
| --- | --- |
| Alpine `linux-rpi` | Образ ядра и штатные модули |
| Alpine `raspberrypi-bootloader` | Загрузочная прошивка Raspberry Pi |
| Пакеты firmware Alpine | Штатные firmware, включая ресурсы Broadcom для выбранной платформы |
| `alcard-kmods-rpi` | `/usr/lib/modules/<ABI>/extra/alcard/*.ko` и `/usr/share/alcard/kmods-rpi-selection.txt` |
| `alcard-firmware-zero` | `/usr/lib/firmware/cardputerzero,st7789v.bin`, `/usr/lib/firmware/bmi270-init-data.fw`, описание источников и уведомление Bosch |
| `alcard-boot-zero` | Общие оверлеи в `/boot/overlays/`, без активного `alcard.cfg` |
| Один APK профиля платы | `/boot/alcard.cfg` |
| `alcard-bsp-zero` | Только точные зависимости, без копирования содержимого |

Оба профиля платы зависят от общего BSP и конфликтуют друг с другом. Общий BSP не выбирает профиль. Обычный профиль включает оверлей BMI270/BMM150; Lite исключает отсутствующие датчики. Источники описывают поддержку камеры, но строка IMX219 в обычной загрузочной конфигурации остаётся закомментированной до проверки соответствующей физической камеры. См. [аппаратную часть](hardware.md).

Сборка модулей выбирает штатные реализации или драйверы производителя по точной конфигурации ядра и экспортируемым символам. Неразрешённое дублирование реализаций или несовпадение ABI должно останавливать сборку. `powerfail_suo` не поставляется. Firmware, DT и данные раскладок имеют отдельных владельцев; заводские `.ko` от другого ядра в систему не копируются. Интеграция Alpine kmod создаёт индексы зависимостей; изолированные проверки также явно вызывают `depmod` для целевого дерева `/usr/lib/modules`.

## Граница пользовательских и сессионных пакетов

| Владелец | Основные файлы или поведение |
| --- | --- |
| `alcard-hello` | `/usr/bin/alcard-settings`, `/usr/sbin/alcard-setupd`, запись меню приложений для настроек, диспетчер tty1, первичная настройка и запуск сессии, конфигурация greetd/PAM, активация/конфигурация BlueZ |
| `alcard-keyboard-zero` | `/usr/share/X11/xkb/symbols/alcard`, `/usr/share/alcard/keyboard/console/*.bmap.gz`, исходные карты и каталог раскладок |
| `alcard-fonts-console` | `/usr/share/kbd/consolefonts/AlcardPixel-*.psf` |
| `alcard-fonts-gui` | `/usr/share/fonts/alcard/AlcardPixel-*.ttf` |
| `alcard-desktop-minimal` | `/usr/libexec/alcard/wayland-session`, файлы резервного labwc и конфигурация Foot |
| `alcard-shell` | `/usr/bin/alcard-shell`, `/usr/libexec/alcard/alcard-radio-helper`, политика polkit для радиоустройств |
| `alcard-polkit-agent` | `/usr/bin/alcard-polkit-agent` |
| `alcard-lock` | `/usr/bin/alcard-lock`, `/etc/pam.d/alcard-lock` |
| `alcard-desktop-shell` | Основной сеанс и клиент Shell, контроль звуковых процессов, основная конфигурация labwc и соответствующие зависимости исполнения |

`alcard-hello` владеет интеграцией NetworkManager/BlueZ, необходимой после установки Console. Он не зависит от удаляемых greetd/labwc/Foot. Hello удаляет определённый набор пакетов графики и входа в систему только при применении Console; оба графических варианта сохраняют Shell и резервную сессию. См. [установку](installation.md) и [безопасность](security.md).

Основная сессия зависит от трёх нативных графических приложений и минимального профиля. Стек PipeWire/WirePlumber и совместимости Pulse/ALSA принадлежит сессии. Минимальный профиль не получает этот стек только ради регуляторов Shell. Клиенты `wpctl`, `pw-dump`, `nmcli`, BlueZ и polkit — зависимости целевой системы; наличие команд в PATH хоста разработчика не подтверждает состав целевых зависимостей.

## Как сборщики создают подписанные APK

[Точка входа сборки](../../build.sh) на хосте вызывает отдельные скрипты в постоянном Alpine aarch64 окружении. Рабочие файлы, кэши, архивы, индексы и APK находятся в игнорируемом каталоге `.alcard-local/`. Сборщики используют `abuild -d`: зависимости и ключи нужно подготовить явно до сборки.

Rust-сборщики используют штатные инструменты Alpine, сохранённые файлы фиксации зависимостей и `cargo build --release --locked --bins`. Полученные ELF и выбранные файлы для исполнения помещаются в детерминированные tar/gzip-архивы. Rust APKBUILD упаковывают эти предварительно собранные файлы; один рецепт не описывает всю процедуру компиляции Rust. Будущий бинарный релиз должен сопровождаться коммитом исходников, файлами фиксации зависимостей и сведениями о сборке.

Отслеживаемые APKBUILD являются шаблонами рецептов. Пустые `sha512sums` заполняются командой `abuild checksum` в одноразовой рабочей копии, затем `abuild` создаёт подписанные пакеты и индексы. Проверка подписи при этом не отключается. M5Stack зафиксирован на коммите `4f7aeee9fc103ebb03d22cac476bb191ecfb321e`; патчи применяются к распакованным исходникам сборки, а не к кешированной копии внешнего проекта.

[Проверка производственной сборки](../../tools/verify-production-build.py) отклоняет артефакты тестов, замеров производительности и примеров, сверяет ожидаемые пути релизных программ и сравнивает установленные программы с релизной сборкой. Проверка установленных пакетов использует точный список разрешённых файлов. Отдельные исходники тестов остаются в Git и не устанавливаются как рабочее содержимое пакета.

Лицензионные объявления относятся к фактическому содержимому. Лицензия проекта не заменяет происхождение BSP под GPL-2.0, условия LCD/Bosch firmware и CC0-шрифтов. См. [лицензирование](licensing.md).

## Политика зависимостей и обновлений

Изменения ядра выпускаются согласованным комплектом:

1. Получить соответствующие `linux-rpi` и `linux-rpi-dev` выбранной стабильной ветки Alpine.
2. Повторно проверить Kconfig, `Module.symvers`, поставщиков, ABI модулей и `MODPOST`.
3. Пересобрать модули и затронутые пакеты firmware, DT и профилей.
4. Проверить оба взаимоисключающих профиля в чистых rootfs.
5. Проверить фактический загрузочный комплект и оборудование перед выпуском поддерживаемого релиза.

Закрепление версии в зависимости APK защищает разрешение зависимостей, но не синхронизирует FAT и не сохраняет старые модули ядра при A/B-пробе. Текущий образ также закрепляет ядро в `/etc/apk/world`. Будущий релиз нового ядра требует явного изменения закреплённой версии world и сохранения старого дерева ABI на нужное время. Принудительные опции и ручные изменения базы пакетов не относятся к обычной процедуре обновления. См. [загрузку и обновления](boot-updates.md).

## Публикация репозитория ещё предстоит

Текущие сборщики используют подписанный локальный репозиторий `.alcard-local/packages/alcard/aarch64/`. Созданный образ содержит Alpine `v3.24/main` и `v3.24/community`; публичный канал обновлений Alcard пока не настроен. Некоторые пользовательские/сессионные версии Alcard закреплены в `world`, поэтому их политику обновления также нужно определить.

Будущему публичному каналу нужны доверенный публичный ключ и его отпечаток, подписанный индекс, разделение архитектур и веток Alpine, полные совместимые комплекты пакетов, сохранение точных входных APK внешних проектов и документированная ротация ключей. Приватные ключи подписи остаются вне Git и обычных релизных артефактов. Перевод из тестового канала в стабильный должен соответствовать фактическому уровню приёмки. Автоматический механизм обновления BOOT не реализован.

## Границы проверок

- `verify-bsp*` проверяет подписанные аппаратные пакеты, ABI, firmware и объединённый Device Tree/Kconfig.
- `install-verify*` использует изолированное корневое дерево зависимостей с `--usermode --no-scripts`; это не загрузочный образ.
- `shell-install-verify` проверяет подписанные пользовательские/сессионные пакеты в одноразовом Alpine rootfs.
- Сборщики образов выполняют реальные пакетные скрипты/триггеры и `mkinitfs`; офлайн-проверка исследует готовые файловые системы.
- Приёмка в виртуальной машине проверяет пользовательскую среду на `linux-virt`; физическое поведение Cardputer и выбор загрузки Raspberry Pi остаются отдельными проверками.

Полная последовательность приведена в [сборке](building.md), область тестов — в [проверках](testing.md), границы готовности — в [текущем статусе](status.md).
