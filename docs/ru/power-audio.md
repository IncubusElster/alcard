# Питание, дисплей и звук

**Язык:** Русский · [English](../en/power-audio.md)

> Область: текущее дерево исходников · Обновлено: 2026-11-22

Полная сессия Graphics владеет политиками Shell для idle, питания outputs, батареи и сна, а также запускает пользовательский стек PipeWire. Graphics Minimal и Console автоматически не запускают эти политики Shell или этот аудиостек. Одного наличия установленных пакетов недостаточно для активности политики. [Настройки](settings.md) описывают текущий UI конфигурации, [рабочий стол](desktop.md) — навигацию быстрых настроек, [безопасность](security.md) — настоящую блокировку сессии.

## Конфигурация и значения по умолчанию

Используйте Settings → «Экран и питание» либо измените общий `$XDG_CONFIG_HOME/alcard/shell.toml` (обычно `~/.config/alcard/shell.toml`) и запросите SIGHUP конкретному PID работающей Shell. Settings атомарно сохраняет полный проверенный кандидат и сама запрашивает перечитывание.

```toml
schema_version = 1
theme = "classic"

[idle]
lock_after_seconds = 300
screen_off_after_seconds = 360

[battery]
low_percent = 20
critical_percent = 5
suspend_on_critical = false
```

Общие ключи размещайте до TOML-таблиц. Это значения по умолчанию, а не свидетельство поддержки всех операций конкретным устройством.

| Параметр | Допустимые значения и действие |
| --- | --- |
| `idle.lock_after_seconds` | Целое число 0–86 400 секунд; ноль отключает автоматическую блокировку |
| `idle.screen_off_after_seconds` | Целое число 0–86 400; ноль отключает автоматическое гашение; положительное значение требует положительного lock timeout и должно быть не меньше него |
| Оба idle-значения равны нулю | Отключение обоих idle-действий |
| `battery.low_percent` / `critical_percent` | Целые проценты, удовлетворяющие `1 <= critical_percent < low_percent <= 100` |
| `battery.suspend_on_critical` | Boolean; автоматический suspend при критической батарее включается явно |

Неизвестные поля, неверные типы, повторные ключи и некорректные сочетания отклоняют весь кандидат. Конфигурация ограничена 16 КиБ. Ошибочное перечитывание сохраняет последнюю корректную политику. Успешная idle-перенастройка начинает новые интервалы уведомлений и восстанавливает outputs, которыми владела прежняя политика гашения. Перенастройка батареи требует свежего наблюдения и не возвращает уже израсходованную попытку автоматического suspend. Полные правила тем/CLI/перечитывания — в [рабочем столе](desktop.md).

## Блокировка по неактивности и питание outputs

Shell использует общие для композитора уведомления `ext-idle-notify-v1` для каждой seat. Она не выводит неактивность из собственного фокуса, не опрашивает ввод и не запускает отдельный поток с настенными таймерами неактивности. Обычный запрос idle notification учитывает compositor idle inhibitors. Для действия все отслеживаемые seats должны простаивать; новая seat начинает активной.

При достижении срока блокировки Shell запрашивает обычный production locker. Гашение разрешено только после **актуального нативного lifecycle-подтверждения `LOCKED`**. Наличия процесса, lock journal или имени на session bus недостаточно. При отказе блокировки дисплей остаётся включённым, появляется диагностика, и тот же idle-период не порождает locker повторно. Ручная блокировка доступна и без поддержки idle notification композитором.

Активность ввода включает outputs, погашенные Shell, но сессия остаётся закрытой до PAM unlock. Позднее lock acknowledgement после активности не может погасить дисплей для старого idle-поколения. Unlock и resume начинают новый интервал. После перезапуска Shell живой locker сохраняется, однако его вспомогательное присутствие не разрешает гашение без нового нативного подтверждения.

Питание outputs использует `zwlr_output_power_manager_v1` на существующем Wayland connection. Меняется power mode, а output не удаляется из расположения рабочего стола. Код раздельно отслеживает желаемое и подтверждённое состояния: запрос включения должен перекрыть ожидающий off, даже если последнее подтверждённое состояние ещё on. Hotplug и удаление протокола обрабатываются явно.

При старте/перечитывании новый управляемый output, сообщивший off, восстанавливается в on. Если гашение отключено, Shell делает это один раз и освобождает исключительное power control. Отвергнутый объект управления не повторяется на каждом кадре или таймере; соответствующий hotplug/перечитывание может создать новую binding. Штатное завершение по возможности отправляет on и освобождает владение; после SIGKILL новая Shell восстанавливает on при получении контроля. Отсутствие/ошибка протокола видны как недоступность, а не мнимое успешное изменение дисплея.

## Яркость

Быстрый регулятор Shell находит ровно одно однозначное устройство `/sys/class/backlight` и читает его `brightness` и `max_brightness`. Проверяются ограниченные числовые чтения, безопасные имена, canonical identity устройства, inode и диапазон; несколько кандидатов дают недоступность вместо произвольного выбора. Чтение использует фиксированные пути sysfs с nonblocking/type checks, а не пользовательские пути.

Изменения выполняются через elogind `Session.SetBrightness("backlight", name, value)` текущей проверенной активной локальной графической сессии. Shell не пишет sysfs напрямую, не меняет права, не добавляет широкие группы доступа и не запускает root brightness helper. Операция привязывается к уникальному владельцу login1, настоящим UID/PID, session и seat и перепроверяет identity устройства до/после изменения.

Left/Right меняет уровень примерно на пять процентных пунктов сырого диапазона. Обычная нижняя цель — `ceil(max_brightness / 100)`, минимум один сырой шаг; Shell намеренно не снижает нормальный положительный уровень до нуля. Значение, уже установленное извне ниже этого предела, Decrease не уменьшает ещё сильнее. Это настроенные ядром единицы яркости, а не измеренная светимость панели, фактический PWM duty или доказательство экономии энергии.

В **Settings TUI есть отдельная привилегированная операция brightnessctl, принимающая 0–100%**. Её нулевое значение не покрывается ненулевым пределом Shell и само по себе не означает предварительную блокировку сессии. Физическое поведение панели и пригодная минимальная яркость остаются предметом приёмки.

## Аудиостек сессии

Полный Graphics запускает PipeWire, WirePlumber и pipewire-pulse через принадлежащий сессии helper `audio-session`. Пакеты включают ALSA-интеграцию PipeWire и инструменты. Launcher использует существующую приватную session D-Bus и настоящий `XDG_RUNTIME_DIR`; systemd user units и root audio daemon не нужны. Helper удерживает runtime lifetime lock, проверяет процесс-владелец сессии и отслеживает точные PID/start time каждого принадлежащего ему daemon.

Существующий чужой audio endpoint даёт явную недоступность, а не user-wide kill, удаление socket или захват управления. Унаследованные remote/runtime-переопределения очищаются; этот стек владеет локальным `pipewire-0` и session Pulse socket. Штатное завершение останавливает только свои процессы. Ожидание в простое не опрашивает систему и не удерживает Python supervisor. При сбое стека Shell остаётся работоспособной, а новый выход/вход повторяет инициализацию; повторное открытие или обновление громкости не перезапускает daemons.

Для страницы Sound в Minimal и Console нужны отдельно доступные пользовательские аудиослужбы. Этот стек Graphics не запускается скрыто. Полного редактора routes/profiles нет; **текущая Settings TUI уже умеет выбирать доступный Audio/Sink как выход по умолчанию**.

### Громкость и mute

Shell управляет фактическим `default.audio.sink` WirePlumber, а не первой звуковой картой, произвольным node или микрофоном. Left/Right меняет программную громкость примерно пятибалльными шагами в пределах 0–100% unity; 5/Space переключает настоящий software mute независимо от аппаратного mute switch кодека. Нулевая громкость и mute — разные состояния.

Показанный уровень вычисляется по наибольшему значению канала. Если другой клиент установил хотя бы один канал выше unity, Shell показывает `100%+` и запрещает дальнейшее повышение или unmute до уменьшения громкости. Изменение громкости задаёт общий уровень каналов и не обещает сохранить прежний баланс. Программный предел не является утверждением об акустической безопасности, громкости динамика или физической настройке 0 dB ES8389.

Текущий backend — PipeWire; автоматического direct-ALSA fallback нет. Старые сырые значения mixer и эксперименты с усилением кодека относятся к датированным записям проверок и не должны применяться как актуальная инструкция управления Shell.

### Ограниченное управление и проверочное чтение

Яркость и звук используют один ограниченный worker с одним ожидающим запросом. Открытие/обновление регуляторов выполняет discovery, изменение — свежие проверки и readback. UI не блокируется на D-Bus/подпроцессах, не выдаёт запрошенный результат за фактический, не повторяет изменение автоматически и не отбирает фокус при позднем ответе. Request ID отсекает устаревшие ответы.

Discovery яркости и звука имеет по шесть секунд; суммарное обновление может занять сумму этих бюджетов. Каждому изменению выделен единый шестисекундный бюджет на всю работу. Дочерние команды используют фиксированные абсолютные пути и отдельные аргументы, ограниченный stdout/stderr и очистку только собственных просроченных детей.

Звук использует `/usr/bin/pw-dump -N -r pipewire-0` и `/usr/bin/wpctl` с `LC_ALL=C`. Полный ограниченный снимок графа фиксирует PipeWire core cookie, фактические default metadata, ID и serial Audio/Sink, устройство и активный route. Device Route properties имеют приоритет над Node Props; проверяются все каналы. Вывод графа ограничен 1 МиБ/1 024 объектами, параметры — 128, каналы — 64; обычный вывод команд/ошибок ограничен 64 КиБ.

Обновление использует один снимок графа; изменение — свежий снимок → фиксированное действие wpctl → свежий readback без повторной записи. Перезапуск сервера, смена default, hotplug, изменение identity/диапазона, timeout и противоречивый readback могут дать Changed/Unknown/Unavailable. Отдельные CLI-соединения не обеспечивают глобальный атомарный compare-and-set относительно другого mixer-клиента; проверки выявляют важные гонки, но не заявляют такую блокировку. Более простые TUI-регуляторы Sound используют ту же пользовательскую службу, однако реализованы отдельно от полной проверки каналов/routes Shell.

## Ручной suspend

Девятая строка быстрых настроек открывает подтверждение сна. 4/Enter подтверждает, 8/Esc отменяет. Shell требует неинтерактивный `CanSuspend=allowed`, корректную текущую локальную user/session/seat, поддерживаемый API и проверки inhibitors, а также готовый sleep monitor. Необходимость аутентификации показывается как ограничение; скрытого административного запроса и обхода политики в этом сценарии нет.

Подготовка связана с request ID и эпохой владельца login1. Её срок — восемь секунд, затем десять секунд на lock. Тот же production locker должен подтвердить `LOCKED`. Координация ждёт применения всего event batch, поэтому более поздний `UNLOCKED`, неопределённость, потеря сессии или отмена по батарее из этого же batch отзывают разрешение до использования worker. Worker проверяет отзывное разрешение непосредственно перед отправкой.

Backend повторяет session/capability/inhibitor-проверки и отправляет `SuspendWithFlags` только с `ROOT_CHECK_INHIBITORS`. Не используются force/skip-inhibitor, повтор аутентификации и fallback на выключение. Back/Home могут отменить подготовку, пока соответствующим вводом владеет Shell и запрос не отправлен; уже запущенный locker они не завершают. После получения ввода locker его Esc отменяет только PAM. После отправки suspend «Назад» лишь скрывает результат и не обещает отозвать запрос.

Принятый method call не доказывает, что устройство физически заснуло. Связанные `PrepareForSleep(true)` и последующий `false` образуют наблюдаемый цикл; одинокий false не выдумывает завершённый цикл. Неопределённый отправленный запрос сохраняет запрет повторной отправки. Запрет снимается только соответствующим наблюдаемым циклом либо свежей эпохой службы с проверенным отсутствием подготовки и новым delay inhibitor; прежняя операция остаётся неизвестной, а не объявляется успешной задним числом.

## Внешний сон и resume

Независимый sleep monitor подписывается до объявления готовности, читает фактическую подготовку и владеет file descriptor delay inhibitor типа `sleep`. Он может обработать внешний `PrepareForSleep(true)`, пока ручной suspend RPC ещё ждёт ответ. Monitor запрашивает locker без смены основного экрана Shell и освобождает собственную задержку только после подходящего нативного lock acknowledgement для той же epoch/cycle.

Delay inhibitor ограничен сроком `InhibitDelayMaxUSec` службы и **не является бессрочным veto внешнего suspend**. При отказе lock Alcard удерживает задержку вместо объявления успеха, но служба может продолжить после истечения своего лимита. На внешний цикл предусмотрена одна попытка блокировки. Потеря владельца отзывает ожидающие разрешения; переподключение восстанавливает наблюдение и не повторяет прежнее системное изменение.

При наблюдаемом resume monitor снова получает inhibitor, отменяет старые намерения ввода/idle, запрашивает включение outputs и сохраняет текущие UI, редактор, выбор и историю уведомлений. Настоящий native lock остаётся закрытым до успешного PAM. Shell не сбрасывает яркость, громкость и default audio sink. Регуляторы устройств обновляются при следующем discovery, а политика батареи требует наблюдения после resume вместо повторного использования отсчёта до сна.

## Политика низкого заряда

Пороги по умолчанию — низкий заряд 20%, критический 5%; автоматический suspend выключен. Автоматическое действие может определять только одна однозначная системная батарея с корректной ёмкостью 0–100%, известной identity источника и явным `Discharging`. Батареи `scope=Device`, отсутствующая/неправильная ёмкость, неоднозначные несколько батарей, исчезнувший источник и неизвестное состояние заряда не подходят. Отсутствие необязательного атрибута `present` само по себе не означает отсутствия батареи; фактические данные всё равно должны пройти проверку. Неизвестная телеметрия внешнего питания не выдумывается как «отключено»; явный Discharging остаётся полезным и без сведений о внешних источниках.

Status worker читает данные каждые пять секунд, выдаёт sequence даже неизменившимся значениям и ставит время **начала** чтения. Объединение доставки не обновляет возраст старых данных. Отсчёт должен быть моложе 15 секунд и новее соответствующего барьера resume/configuration/lock. Потеря данных отменяет действие; настоящие 0% остаются корректным критическим значением.

Эпизод представляет одно внутреннее уведомление. Вход в low предупреждает один раз; вход в critical один раз обновляет/усиливает предупреждение. Обновления процента/языка не создают нового unread-события или баннера, а удаление пользователем не заставляет следующий poll создать запись заново. Предупреждения учитывают обычное подавление баннеров аутентификацией/lock и не отбирают фокус или принудительно открывают Home. Charging, Full или подтверждённое внешнее питание завершают эпизод. При разряде полное восстановление требует уровня выше `low_percent` и не ниже `min(low_percent + 3, 100)`.

Критическая полоса предупреждения использует гистерезис в три процентных пункта. Однако ожидающий автоматический сон отменяется **сразу после свежего значения выше `critical_percent`**, не дожидаясь окончания визуального гистерезиса. Смена источника и устаревшая телеметрия не возвращают использованную попытку. При resume временный запрет предотвращает немедленный повторный сон; свежее восстановление выше критической полосы может снять этот временный запрет, но потраченная автоматическая попытка остаётся потраченной на весь эпизод разряда.

### Явно включаемый автоматический suspend

При включённой опции и свежем критическом заряде политика расходует единственную попытку **до** передачи управления сценарию сна. Это включает ошибки, отказы, отмены и неизвестные результаты. Сначала сохраняется attempt marker, запрашивается связанное обновление доступности со сроком восемь секунд, затем используется та же неинтерактивная предварительная проверка и native lock-before-suspend coordinator, что для ручного сна.

После подтверждения locker требуется ещё одно свежее чтение батареи, начатое после lock barrier. Charging, восстановление порога, потеря данных и отмена из всего event batch применяются до отправки. Разрешение истекает вместе с наблюдением батареи и отзывается, если эпизод перестал подходить. Ошибка показывает причину и сохраняет уже полученный lock; она не включает принудительное выключение, не игнорирует inhibitors и не повторяет suspend по кругу.

Runtime-журнал `$XDG_RUNTIME_DIR/alcard-battery-inhibit-v1` сохраняет запрет попытки/resume при перезапусках Shell в том же времени жизни runtime. Проверяются владелец, режим, тип обычного файла, inode и содержимое; создание исключительное, очистка удаляет только ожидаемое состояние. Повреждённый или недоступный журнал отключает автоматический suspend на всё время жизни процесса до перезапуска вместо разрешения новой попытки. Настоящая зарядка/восстановление очищают корректные markers через политику; ручное удаление marker — не обычная процедура восстановления. Это runtime-защита, а не долговечная история между загрузками.

## Проверка и карта исходников

State machines исходников и изолированные fixtures проверяют сроки, readback, гонки и отказы. Сценарии установленных APK и native VM должны указывать точные исходники и комплект пакетов. Они не доказывают фактическую яркость Cardputer, акустический выход, пороги зарядки, физический suspend, wake и энергопотребление. [Аппаратная платформа](hardware.md), [проверки](testing.md) и [текущий статус](status.md) определяют оставшуюся приёмку.
