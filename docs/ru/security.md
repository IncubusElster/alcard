# Аутентификация, блокировка сессии и восстановление

**Язык:** Русский · [English](../en/security.md)

> Область: текущее дерево исходников · Обновлено: 2026-11-22

Alcard разделяет вход, административную авторизацию и разблокировку экрана. Shell показывает действия и наблюдает события жизненного цикла; она не получает пароли и не решает, разрешена ли системная операция. Для сообщения об уязвимости следуйте [политике безопасности](../../SECURITY.ru.md) репозитория. Ниже описаны контракты текущей реализации, а не завершённая аппаратная оценка безопасности.

## Границы процессов и полномочий

| Назначение | Компонент | Фактический источник полномочий |
| --- | --- | --- |
| Первоначальная настройка машины и аккаунта | `alcard-settings --hello` и root `alcard-setupd` | Защищённый first-boot backend, проверенный план и отдельные credentials через stdin |
| Вход | greetd/agreety с login-профилем PAM Alcard | Дистрибутивные auth/account-модули и обязательная регистрация сессии через `pam_elogind` |
| Установленные терминальные настройки | Settings TUI и allowlist настроек setupd | doas или su в терминале; разрешения целевого backend |
| Графический административный запрос | Отдельный непривилегированный `alcard-polkit-agent` | polkit Authority, нативный authentication helper и дистрибутивный PAM |
| Разблокировка экрана | Отдельный непривилегированный `alcard-lock` | `ext-session-lock-v1` композитора и PAM для текущего реального UID |
| Радиоизменение/поиск, требующие прав | Helper с фиксированными операциями | Установленная политика действий pkexec и polkit |
| Операции питания сессии | login1-клиент Shell | Проверенная текущая сессия, политика elogind и inhibitors |

Будущий графический Settings frontend должен использовать общие операции настроек с подходящим графическим адаптером авторизации. Существующая polkit-форма не является Settings frontend. Терминальный doas/su в текущей TUI также выбран намеренно: он не перенаправляется в невидимый графический запрос пароля.

## Первый запуск и административный доступ

Hello принимает пароль обычного пользователя, необязательный доступ doas и необязательный пароль root. Нужен хотя бы один административный путь:

| Выбран doas | Задан пароль root | Доступные административные identities |
| --- | --- | --- |
| Да | Нет | Пользователь Hello; пароль root заблокирован |
| Да | Да | Пользователь Hello и root |
| Нет | Да | Root |
| Нет | Нет | Некорректный план: нет административного пути |

Credentials передаются отдельно от несекретного плана через stdin, а не аргументы команд, журналы или progress markers. Привилегированный backend повторно проверяет план, состояние машины, выбранную сессию и административные файлы до создания аккаунта или изменения пароля. Пароль пользователя задаётся до создания административного пути. Замещающий путь root создаётся до того, как повторная попытка может отозвать doas; root блокируется лишь после появления работающей политики doas. Первый запуск — защищённая возобновляемая операция, а не транзакционный откат всех изменений системы.

Управляемые файлы — `/etc/doas.d/alcard.conf` (root, 0600) и, при графической установке, `/etc/polkit-1/rules.d/49-alcard-admin.rules` (root, 0644). Проверяются родительские каталоги, владелец, режимы и типы файлов; симлинки, небезопасные пути и чужое содержимое политики отвергаются до изменения аккаунта. Повторная попытка согласует только точную известную политику Alcard для того же progress account. Alcard не заменяет произвольные правила администратора.

Правило doas требует пароль пользователя. Проверка читает все применимые доверенные конфигурации doas, проверяет синтаксис и запускает probe под реальным аккаунтом с фактическими UID, GID и дополнительными группами. Неинтерактивная проверка — фиксированная безвредная команда `doas -n -u root /bin/ash -c 'exit 0'`. Только ожидаемый результат «требуется аутентификация» подтверждает выбранный парольный путь; nopass, отказ и неожиданный вывод не подходят. Probe ограничен пятью секундами и объёмом stderr; этот stderr не публикуется как пользовательская диагностика.

Созданный polkit `addAdminRule` действует для запрашивающего пользователя Hello в активной локальной сессии и выбирает настроенные identities. Он не возвращает разрешение операции, не обходит PAM и не добавляет широкие группы доступа к устройствам. Политика конкретного действия в дистрибутиве по-прежнему решает, нужна ли аутентификация и допустима ли операция. Ошибки setup показывают фиксированный этап и разрешённую причину/вид ошибки, а не сырой вывод подпроцесса, способный содержать credentials.

## Настоящий вход и владение службами

У tty1 один диспетчер. До завершения он запускает Hello; затем — greetd при установленном графическом login stack либо getty. Конкурирующей самостоятельной OpenRC-службы greetd нет. Последовательная консоль после Hello остаётся путём getty. Выделенный аккаунт `greeter` заблокирован и неинтерактивен; он не является вошедшим пользователем.

Пользовательский вход использует `/etc/pam.d/alcard-greetd` с базовыми дистрибутивными auth/account/password/session-модулями и **обязательным `pam_elogind.so type=wayland`** до session launcher. У аутентификации greeter свой дистрибутивный сервис. Launcher требует обычного пользователя, приватный настоящий `XDG_RUNTIME_DIR` и действительную seat/session; используется `LIBSEAT_BACKEND=logind`. Строка окружения вроде `XDG_SESSION_ID` не создаёт аутентифицированный вход.

OpenRC владеет системной D-Bus, предпосылками устройств и cgroups. Elogind использует дистрибутивную активацию через system D-Bus; второго конкурирующего supervisor elogind нет. Оба графических режима требуют корректного PAM/runtime-контракта, хотя Minimal не запускает полный supervisor Shell. Подробности установки и владения режимами — в [установке](installation.md).

## Графический polkit-agent

`alcard-polkit-agent` регистрирует стандартный AuthenticationAgent для своей настоящей Unix login-сессии. Он привязывается к уникальному владельцу polkit Authority на system bus и принимает запросы аутентификации только от него. GIO/GLib и нативный `PolkitAgentSession` ведут PAM-разговор через доверенный дистрибутивный helper. GUI не умеет «выдать права» на основании состояния формы.

Один worker владеет нативными сессиями, главный поток — Wayland-поверхностью. Callbacks помещают события в очередь; уничтожение сессии и завершение D-Bus invocation происходят после возврата из callback. Ответ содержит request ID и новый prompt serial, используется один раз и не может ответить на более поздний prompt. Единственная разрешённая identity выбирается автоматически; несколько требуют явного выбора. Сохраняются точные индексы Authority и числовые UID. Неизвестный, дублирующийся, пустой или слишком большой набор identities отклоняется вместо неявного выбора root.

Активный запрос использует layer-shell overlay 320×170 с клавиатурным фокусом только во время показа. Видны действие, причина, разрешённая identity, PAM prompt и ошибка. F1 открывает ограниченные прокручиваемые подробности; стрелки выбирают identity или прокручивают. Доступны общие темы Classic/Emerald, EN/RU/ES, индикаторы Caps Lock и XKB-группы. Enter выбирает/отправляет либо явно повторяет, Esc отменяет, Backspace удаляет символ, Ctrl+U очищает. При вводе цифры 4–8 являются текстом, а удержанные/повторные клавиши не подтверждают после получения фокуса.

Неверная аутентификация допускает явный повтор: не более трёх попыток и пяти минут на запрос; PAM/polkit могут быть строже. Потеря фокуса, клавиатуры, output, поверхности, login-сессии или Authority отменяет незавершённую работу. Отмена не отзывает задним числом уже выданное Authority разрешение. Скрытого TTY fallback нет.

Все ответы PAM маскируются, включая echo-on prompts и одноразовые коды. Вставка из буфера и text-input/IME не реализованы; символы вводятся активной XKB-раскладкой. Буфер секрета допускает 512 байт/128 Unicode-символов, не имеет представления Clone/Debug и очищает удалённые байты, а при отправке, отмене и уничтожении — весь буфер. Renderer получает только длину маски. Production отключает core dumps и dumpability и отвергает `POLKIT_DEBUG`, `G_DBUS_DEBUG`, `WAYLAND_DEBUG`. Штатный переход привилегий доверенного helper намеренно сохраняется; `NO_NEW_PRIVS` для этого пути не установлен.

Прямой диагностический запуск внутри существующей Wayland login-сессии обычного пользователя:

```sh
alcard-polkit-agent --locale ru --theme classic
```

Агенту нужны system/session D-Bus, polkitd, PAM/helper, настоящая регистрация elogind/logind, приватный runtime и layer-shell. Не запускайте его через sudo. Второй агент не заменяет зарегистрированный. Сборочный контейнер без login-сессии подходит для unit-тестов; production-регистрация в нём корректно завершается отказом.

Во время активности агент владеет `org.alcard.Authentication` на session bus. Shell использует присутствие только для подавления баннеров с сохранением истории. Подмена этого сигнала представления может мешать показу, но не разрешает операцию. Layer overlay не является механизмом secure attention против скомпрометированного композитора.

## Блокировка сессии и PAM текущего пользователя

Восьмая строка быстрых настроек запускает блокировку через 4/Enter без дополнительного подтверждения. Shell ищет production locker рядом со своим исполняемым файлом, а не через PATH или переменную подмены helper. Один locker обслуживает ручную, idle- и связанную со сном блокировку. Поддержан и прямой запуск внутри Wayland-сессии текущего пользователя:

```sh
alcard-lock
alcard-lock --locale ru --theme classic
```

Locker отвергает root, setuid/setgid-запуск и несовпадение реальной/эффективной identity. Он проверяет фиксированный `/etc/pam.d/alcard-lock`: непустой обычный файл root без записи для группы/остальных, без симлинка/FIFO. Пакет устанавливает подходящий дистрибутивный профиль с режимом 0644. Alpine использует `base-auth`/`base-account`, Ubuntu/Debian — `common-auth`/`common-account`.

Клиент запрашивает **`ext-session-lock-v1`**, создаёт непрозрачные lock surfaces для всех текущих outputs и покрывает новые при hotplug. Аутентификация начинается только после подтверждения `locked` композитором. Общая реализация SHM ограничивает поверхность 4 096 пикселями по стороне и 4 194 304 пикселями суммарно; неподдерживаемые размеры и прочие ошибки не должны открывать путь к unlock. Смерть процесса, отсутствие протокола, ошибка output, timeout и отказ PAM не отправляют unlock. После подтверждённой композитором блокировки авария locker оставляет abandoned lock согласно протоколу.

На заблокированной заставке 4/Enter открывает ввод пароля. Цифры 4–8, Space и буквы — текст пароля; Enter отправляет, Backspace удаляет, Ctrl+U очищает. Esc отменяет только текущую попытку аутентификации и возвращает на всё ещё заблокированную заставку. Потеря фокуса также отменяет попытку. Все ответы PAM остаются скрытыми.

Отдельный дочерний процесс того же бинарника обслуживает PAM через ограниченные анонимные pipes. Сервис фиксирован как `alcard-lock`; имени пользователя, пароля и выбираемого сервиса нет в аргументах/окружении. Нужны успешные `pam_authenticate(PAM_DISALLOW_NULL_AUTHTOK)` и `pam_acct_mgmt`, после чего проверяется соответствие итогового `PAM_USER` тому же реальному UID. Новая login-сессия не открывается, пароли не меняются, пароль другого администратора не принимается за identity владельца сессии.

Для секретов действуют те же 512 байт/128 символов и явная очистка. У каждой попытки/prompt свои generation/serial. Отменённый ответ или старый успех не разблокирует более новую попытку. Срок аутентификации — 120 секунд; отмена/timeout завершает только собственную PAM process group, сохраняя блокировку. Core dumps и dumpability отключены; штатный переход привилегий доверенного `unix_chkpwd` остаётся доступным. `WAYLAND_DEBUG` запрещён.

Только актуальный успешный PAM разрешает `unlock_and_destroy`. Locker сообщает о завершении после отдельного Wayland sync acknowledgement. Shell получает только lifecycle-события (`FAILED` до блокировки, `LOCKED`, `UNLOCKED`), а не секреты или право unlock. Смерть Shell не завершает независимый locker. Имя `org.alcard.SessionLock` на session bus подавляет Home/баннеры как вспомогательный сигнал; его потеря или подмена не разблокирует композитор.

В production нет демонстрационного пароля, обхода, подмены helper, режима снимков и IPC-команды unlock. `--pam-worker` — внутренний вход в настоящий PAM backend; он не может разблокировать без session-lock object GUI. Тестовые SHM-снимки пустых форм отличаются от снимков композитора и не доказывают доступность screencopy при блокировке.

## Восстановление после сбоев и потеря сессии

Восстановление использует общий журнал `alcard-lock-state`, а не PID-файл, выдаваемый за подтверждение блокировки. Identity берётся из peer credentials **подключённого Wayland socket** и включает UID композитора, PID и время старта процесса. Файл — `$XDG_RUNTIME_DIR/alcard-lock-v1-<pid>-<start>.state`, в принадлежащем пользователю runtime-каталоге 0700. Это обычный файл 0600 с одной жёсткой ссылкой и проверенной идентичностью inode/пути; симлинки, подмена и небезопасный владелец отвергаются.

Живой locker удерживает исключительную lease на том же inode. Он записывает намерение до запроса lock; авария освобождает kernel lease, но сохраняет намерение. Shell наблюдает изменения через inotify и перезапускает abandoned locker с задержкой от одной до 30 секунд. Живой locker сохраняется при перезапуске Shell. Замена должна получить собственный protocol lock и пройти свежий PAM. Только locker очищает намерение после аутентифицированного unlock и Wayland sync; неизвестное или повреждённое состояние никогда не считается доказательством unlock. У нового времени жизни композитора отдельная identity.

Supervisor сессии Graphics владеет Shell, polkit и своим необязательным аудиостеком; перед отправкой сигналов собственным детям проверяет PID start time. Поведение восстановления определено явно:

| Сбой | Поведение |
| --- | --- |
| Shell завершилась | Перезапуск с задержкой; существующий locker не уничтожается |
| Locker завершился после lock | Сохранение compositor lock; замена через abandoned-intent с обязательным новым PAM |
| Сбой только агента/polkit Authority | Отмена запроса; перезапуск/регистрация для той же действующей login-сессии |
| Потеря настоящей login binding, elogind, system bus или private session bus | Агент сообщает SessionLost кодом 75; управляемое завершение сессии и возврат к greetd для нового PAM-входа |
| Сбой аудиостека | Диагностика с сохранением рабочего стола; повтор стека при новом входе |

Восстановление не выдумывает новый session ID и не использует устаревшую аутентификацию. Graphics Minimal намеренно имеет более простой жизненный цикл Foot и не наследует все гарантии наблюдения полного Graphics.

## Ограничения, исходники и проверка

Явная очистка секретов снижает экспозицию в собственных буферах Alcard, но не доказывает удаление всех копий из PAM, библиотек, ядра или swap. Root и скомпрометированный композитор находятся вне защиты этих пользовательских клиентов. Настоящее подтверждение протокола, успешный PAM и действительная login binding остаются обязательными; имена служб, наличие журнала, существование процесса и снимки экрана их не заменяют.

Тесты исходников и изолированные native/VM-сценарии проверяют разные слои. Нативные harness создают временных пользователей/PAM services только внутри одноразовых контейнеров или VM. Не превращайте эти скрипты в проверки аккаунтов хоста. Аппаратные unlock, изоляция фокуса, настоящий suspend/resume и восстановление остаются отдельной приёмкой; [проверки](testing.md), [аппаратная платформа](hardware.md) и [текущий статус](status.md) сохраняют эти границы.
